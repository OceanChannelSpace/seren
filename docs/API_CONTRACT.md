# SEREN MVP — API Contract & Data Model

**Binding contract** for backend and frontend workers. Do not change endpoint
shapes or field names without updating this file and notifying the
coordinator.

## Data model (SQLite)

### `profiles`

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `name` | TEXT NOT NULL | 1–80 chars |
| `email` | TEXT NOT NULL UNIQUE | valid email format, lowercase-normalized |
| `interests` | TEXT NOT NULL | JSON array of 1–8 strings from the fixed interest list |
| `intention` | TEXT NOT NULL | 10–500 chars, free text |
| `connection_prefs` | TEXT NOT NULL | JSON: `{"seeking":["friendship","practice-partner","collaboration","guidance"],"availability":"…"}` |
| `consents` | TEXT NOT NULL | JSON: `{"introductions":bool,"community_visible":bool,"ai_matching":bool}` |
| `is_seed` | INTEGER NOT NULL DEFAULT 0 | 1 = demo seed member |
| `created_at` | TEXT NOT NULL | ISO timestamp |
| `updated_at` | TEXT NOT NULL | ISO timestamp |

**Fixed interest list** (shared by backend validation and frontend UI):
`meditation`, `tarot`, `astrology`, `breathwork`, `reiki`, `sound-healing`,
`yoga`, `journaling`, `dreamwork`, `numerology`, `crystals`, `shamanism`

**Fixed seeking options:** `friendship`, `practice-partner`, `collaboration`,
`guidance`

### `introductions`

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `requester_id` | INTEGER NOT NULL FK → profiles.id | who asked for the intro |
| `proposed_id` | INTEGER NOT NULL FK → profiles.id | who is proposed |
| `intention` | TEXT NOT NULL | the intention text the request was made with |
| `note` | TEXT NOT NULL | warm intro note generated by the matcher |
| `score` | REAL NOT NULL | match score at request time |
| `status` | TEXT NOT NULL DEFAULT 'proposed' | `proposed` \| `accepted` \| `declined` \| `withdrawn` |
| `created_at` | TEXT NOT NULL | ISO timestamp |
| `updated_at` | TEXT NOT NULL | ISO timestamp |

**Matching rule (deterministic, explainable):**
For a requester R and candidate C (C ≠ R, no non-withdrawn introduction already
exists between the pair in either direction):
`score = 2 × (shared interests) + 1 × (shared intention keywords)`.
Intention keywords = lowercase alphanumeric tokens ≥ 4 chars, minus a small
stopword list. Highest score wins; ties broken by lowest profile id. Only
candidates with `consents.community_visible = 1` are eligible. A candidate
with score 0 is still returned if nothing better exists (note says so
honestly); if no eligible candidates exist, return 404 `no_match`.

**Intro note template:**
`"You and {name} share {n} spiritual {interest|interests}{keyword-bit}. {first-name-requester}, {intention-echo}"` — keep it warm, one or two
sentences. Backend generates it; frontend displays verbatim.

**Status transitions:**
- `proposed → accepted` (POST `/:id/accept`)
- `proposed → declined` (POST `/:id/decline`)
- `proposed → withdrawn` (POST `/:id/withdraw`, requester only — MVP: any
  caller may withdraw since there is no auth; document as simplification)
- All other transitions → 409 with `code: "invalid_transition"`.

## REST endpoints

Base: `/api`. All JSON. Error shape:
`{"error": {"code": "snake_case", "message": "human-readable"}}`.

| Method | Path | Body / Query | Success | Errors |
|---|---|---|---|---|
| GET | `/api/health` | — | 200 `{"status":"ok","seeded":bool}` | — |
| POST | `/api/profiles` | `{name,email,interests[],intention,connectionPrefs,consents}` | 201 profile | 400 `validation_error` (details array), 409 `email_taken` |
| GET | `/api/profiles` | — | 200 `{profiles:[{id,name,interests,intention,is_seed}]}` (public-safe; no email/consents) | — |
| GET | `/api/profiles/:id` | — | 200 full profile | 404 `not_found` |
| PATCH | `/api/profiles/:id` | partial profile fields | 200 full profile | 400, 404, 409 `email_taken` |
| POST | `/api/introductions/request` | `{requesterId,intention}` | 201 `{introduction, proposed:{id,name,interests,intention}, scoreBreakdown:{sharedInterests,sharedKeywords,score}}` | 400 `validation_error`, 404 `requester_not_found`, 403 `consent_required` (requester hasn't opted into introductions), 404 `no_match` |
| GET | `/api/introductions?profileId=` | query required | 200 `{introductions:[{id,requesterId,proposedId,requesterName,proposedName,intention,note,score,status,createdAt}]}` | 400 `validation_error` |
| POST | `/api/introductions/:id/accept` | — | 200 introduction | 404, 409 `invalid_transition` |
| POST | `/api/introductions/:id/decline` | — | 200 introduction | 404, 409 `invalid_transition` |
| POST | `/api/introductions/:id/withdraw` | — | 200 introduction | 404, 409 `invalid_transition` |

**Profile JSON (full):**
`{"id","name","email","interests":[],"intention","connectionPrefs":{"seeking":[],"availability":""},"consents":{"introductions":bool,"community_visible":bool,"ai_matching":bool},"isSeed":bool,"createdAt","updatedAt"}`
(camelCase on the wire; snake_case in the DB.)

**Validation rules (backend enforces; frontend mirrors):**
- `name`: required, 1–80 chars.
- `email`: required, valid format, unique (409 `email_taken`).
- `interests`: array, 1–8 items, each in the fixed list.
- `intention`: required, 10–500 chars.
- `connectionPrefs.seeking`: array, subset of fixed seeking options (may be empty).
- `connectionPrefs.availability`: optional string ≤ 200 chars.
- `consents`: all three booleans required; `introductions` must be `true` to
  create the profile at all (consent-first: no account without intro consent).
  Rationale: the product's core loop is introductions; a profile that cannot
  be introduced is a dead end. Documented, reversible.
- `intention` on intro request: required, 5–500 chars.

## Frontend routes (hash routing)

- `#/` — landing: what SEREN is, how it works (3 steps), spiritual identity,
  CTA "Begin" → `#/profile`.
- `#/profile` — create/edit profile form. New visitor → create; returning
  (localStorage `seren_profile_id`) → edit. Inline validation errors.
- `#/connect` — request introduction: intention textarea (prefilled from
  profile), "Request introduction" button → loading → match card (name,
  shared interests, note, score explanation) → Accept / Decline-and-find-next.
- `#/inbox` — connections grouped by status (proposed / accepted / declined /
  withdrawn), withdraw action on proposed, empty states per group.
- Global: API failure banner with Retry; nav header; footer with demo-seed
  notice.

**Identity:** `localStorage.seren_profile_id`. "Sign out / start over" clears
it (profile row stays in DB — documented).

## Seed data

6 demo members (`is_seed=1`), varied interests/intentions, all consents true.
Labeled "demo seed" in UI. Seeded once at first DB creation
(`SEED_DEMO=true` default); never re-seeded over user data.

## Env vars

`PORT` (default 3000), `DB_PATH` (default `./data/seren.db`), `SEED_DEMO`
(default `true`). Documented in `.env.example`. No secrets exist.
