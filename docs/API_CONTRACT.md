# SEREN MVP — API Contract & Data Model

**Binding contract** for backend and frontend workers. Do not change endpoint
shapes or field names without updating this file and notifying the
coordinator.

**Product taxonomy.** Three connection layers (who connects: Human to Human, Human to vetted benevolent AI, vetted AI to vetted AI) and three connection modes (how connections are found: Data, Synchronicity, Human). Vetted-AI-to-vetted-AI networking is a future protocol — not designed or built in this MVP.

### `introductions`

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `requester_id` | INTEGER FK → profiles.id ON DELETE SET NULL (v11) | who asked for the intro; NULL once they delete their profile |
| `proposed_id` | INTEGER FK → profiles.id ON DELETE SET NULL (v11) | who is proposed; NULL once they delete their profile |
| `intention` | TEXT NOT NULL | the intention text the request was made with |
| `note` | TEXT NOT NULL | warm intro note generated by the matcher |
| `score` | REAL NOT NULL | match score at request time |
| `status` | TEXT NOT NULL DEFAULT 'proposed' | `proposed` \| `accepted` \| `declined` \| `withdrawn` |
| `created_at` | TEXT NOT NULL | ISO timestamp |
| `updated_at` | TEXT NOT NULL | ISO timestamp |

**Matching rule (deterministic, explainable):**
For a requester R and candidate C (C ≠ R, no non-withdrawn introduction already
exists between the pair in either direction):
`score = 2 × (shared interests) + 1 × (shared intention keywords)`.
Intention keywords = lowercase alphanumeric tokens ≥ 4 chars, minus a small
stopword list. Highest score wins; ties broken by lowest profile id. Only
candidates with `consents.community_visible = 1` are eligible. A candidate
with score 0 is still returned if nothing better exists (note says so
honestly); if no eligible candidates exist, return 404 `no_match`.

**Matching v2 (2026-10-01, `/api/discover`):** the curated-Discover engine
(`src/match.js` `findMatches`) extends the rule with complementary factors —
needs↔offers token overlap (3 pts each, max 3 per direction), shared skills
(1 pt each, max 3) — plus shared practices (3), intentions (2), intention
keywords (1), compatible format (2), local/remote alignment (2), and shared
language (1). Scores are internal; the UI shows only qualitative reasons.
**Controlled serendipity:** when `consentSettings.serendipity !== false`
(default on, toggleable in Me → Discovery settings), one lowest-scoring
eligible candidate (score > 0) is appended as a clearly-labeled wild card. It
never displaces ranked results and never overrides consent gates
(blocks, passes, pauses, existing pairs).

**`needsMatching` consent:** when a member sets
`consentSettings.needsMatching` to `false` (default `true`, toggleable in
Me → Discovery settings as "Match me on my needs"), their needs are excluded
from matching in both directions — their needs never score against others'
offers, and others' needs never score against their offers. The flag is
evaluated per side: the requester's setting and each candidate's setting
apply independently.

**Match-reason privacy:** reasons shown to the requester may quote the
requester's own wording back to them, but never quote a candidate's hidden
offers/needs/skills verbatim — generic phrasing is substituted ("something
you're looking for", "something you may be able to offer"). The same rule
applies to bilateral proposal explanations: neither party sees the other's
raw field wording. Reverse complementarity (requester's offer ↔ candidate's
need) is attributed as "looking for something you may be able to offer,"
never "you offer X."

**Intro note template:**
`"You and {name} share {n} spiritual {interest|interests}{keyword-bit}. {first-name-requester}, {intention-echo}"` — keep it warm, one or two
sentences. Backend generates it; frontend displays verbatim.

**Status transitions:**
- `proposed → accepted` (POST `/:id/accept`)
- `proposed → declined` (POST `/:id/decline`)
- `proposed → withdrawn` (POST `/:id/withdraw`, requester only — MVP: any
  caller may withdraw since there is no auth; document as simplification)
- All other transitions → 409 with `code: "invalid_transition"`.

**Agent rules:** agents are always labeled AI and unverified, and never presented
as human. Only the registering operator may edit or hide an agent (403 otherwise).
The platform does not independently verify agent behavior — the operator's
`trustNote` is shown to members as an unverified declaration, never as a
platform endorsement. Agent discovery is gated on
the member's `ai_matching` consent: `/api/discover` suggests agents only with
`?agents=true` and only when `consents.ai_matching !== false`; matching uses
capability↔need token overlap and intention-language overlap.

`/api/health`, `/api/beta/status`, and `/api/beta/enter` returns
403 `beta_required` unless the request carries a valid beta cookie.

**Profile JSON (full):**
`{"id","name","email","interests":[],"intention","connectionPrefs":{"seeking":[],"availability":""},"consents":{"introductions":bool,"community_visible":bool,"ai_matching":bool},"consentSettings":{...},"isSeed":bool,"createdAt","updatedAt"}`
plus v7: `"offers":[]`, `"needs":[]`, `"skills":[]` (free-text lists, max 10,
≤80 chars each; shared with the practices visibility rule).
(camelCase on the wire; snake_case in the DB.)

**Validation rules (backend enforces; frontend mirrors):**
- `name`: required, 1–80 chars.
- `email`: required, valid format, unique (409 `email_taken`).
- `interests`: array, 1–8 items, each in the fixed list.
- `intention`: required, 10–500 chars.
- `connectionPrefs.seeking`: array, subset of fixed seeking options (may be empty).
- `connectionPrefs.availability`: optional string ≤ 200 chars.
- `consents`: all three booleans required; `introductions` must be `true` to
  create the profile at all (consent-first: no account without intro consent).
  Rationale: the product's core loop is introductions; a profile that cannot
  be introduced is a dead end. Documented, reversible.
- `intention` on intro request: required, 5–500 chars.

**`consentSettings` keys** (all optional booleans, defaults applied server-side):
- `discoveryEnabled` (default `true`) — appear in Discover.
- `paused` (default `false`) — pause all matching/introductions.
- `serendipity` (default `true`) — allow the labeled wild-card match.
- `needsMatching` (default `true`) — include my needs in matching.

## Addendum — v3: consent-first connection briefs (2026-09-29)

The guided connection flow sits on top of the above. It is a rule-based guide (deterministic keyword and pattern matching), not an AI model. Guide session
endpoints keep their shapes; the completion response now returns
`proposals: []` until the requester has an active, consent-saved brief
(consent-first: proposals are unlocked by `GET /api/guide/proposals` after
brief approval).

### Schema v3 (`PRAGMA user_version = 3`)

New `briefs` table: `id`, `profile_id` UNIQUE, `who_text`, `intention_text`,
`good_fit_text`, `offer_text`, `logistics_text`, `boundaries_text`,
`shared_text`, `consent_save` (0/1), `consent_share` (0/1),
`status` (`draft`|`active`|`paused`|`withdrawn`), `created_at`, `updated_at`.
All text fields ≤ 2000 chars.

`introductions` gains `requester_shared_text` TEXT (snapshot of the
requester's approved shareable text at request time; empty when no brief
was attached).

A sentinel profile `id = 0` ("SEREN · connector") exists so the warm-intro
system messages (`messages.sender_id = 0`) satisfy the FK. It is excluded
from all listings, discovery, and member counts.

### Brief lifecycle

- `POST /api/briefs` `{profileId, sessionId}` → 201/200 (replace resets to
  draft, clears consent). 404 if the session is missing, foreign, or not
  complete.
- `GET /api/briefs/mine?profileId=` → `{brief}` or `{brief:null}`.
- `PATCH /api/briefs/:id` — owner only; draft/active editable (active stays
  active); paused/withdrawn → 409.
- `POST /api/briefs/:id/approve` `{profileId, shared_text, consent_save,
  consent_share}` → active. Requires `consent_save === true` and
  `shared_text` trimmed 1–600 chars; 400 otherwise; 403 non-owner; 409 if
  withdrawn.
- `POST /api/briefs/:id/pause` → paused; `POST .../resume` → active if it
  was approved (else draft); withdrawn can never be resumed (409).
- `POST /api/briefs/:id/withdraw` → withdrawn.
- Ownership failures → 403 `forbidden`; missing → 404 `not_found`.

### Gated proposals

`GET /api/guide/proposals?profileId=&sessionId=` → 403 `consent_required`
unless the requester has an active brief with `consent_save = 1`.
Success: `{proposals: [...]}` (≤ 3), each proposal:
`{candidate, connectionType, connectionTypeLabel, whyItFits[], forCandidate,
suggestedFirstStep, suggestedFirst (legacy alias), candidateSharedText}`
— `candidateSharedText` only from the candidate's active, share-approved
brief, else `''`. Matching hard-gates candidates on
`consents.introductions === true` plus all pre-existing gates.

### Connections with brief

`POST /api/connections/request` accepts optional `briefId` (positive int).
If present: 403 `brief_invalid` unless it belongs to the requester, is
`active`, and has `consent_share = 1`. The approved `shared_text` is
snapshotted onto the introduction; the list view exposes it as
`requesterSharedText` only. `private_notes` never leave the server.

### Warm introduction

On `respond` `accepted` / `accepted_with_boundary`, SEREN (sender id 0)
posts one deterministic message: first names + each side's approved
`shared_text` (requester: snapshot, falling back to their active
share-approved brief; responder: their active share-approved brief),
truncated ~140 chars each, + a gentle first step derived only from the
connection type. No invented facts, no certainty language. Declines post
no message.

## Addendum — v4: conversational guide chat (2026-09-29)

The scripted guide engine runs as a chat thread. Bot copy is warm and
grounded (never clinical/medical/psychic-certainty/spiritual-authority
claims; SEREN never claims to be human); every bot text ≤ 400 chars.

### Schema v4 (`PRAGMA user_version = 4`)

New `chat_sessions` table: `id`, `profile_id`, `guide_session_id` (nullable),
`brief_id` (nullable), `stage` (`start` | `seeking` | `followup` |
`brief_review` | `editing` | `proposals` | `confirm_replace` | `resume_offer`),
`pending_question_id` (nullable), `pending_field` (nullable),
`transcript_json` (JSON array of message objects, capped at 60 entries),
`created_at`, `updated_at`. Index on `profile_id`.

### Endpoints

| Method | Path | Body / Query | Success | Errors |
|---|---|---|---|---|
| POST | `/api/chat/start` | `{profileId}` | 201 `{session:{id,stage}, messages[], quickReplies?, proposals?, brief?}` | 400 `validation_error`, 404 profile |
| POST | `/api/chat/message` | `{profileId, sessionId, text}` (text 1–2000 chars) | 200 `{session:{id,stage}, messages[], quickReplies?, proposals?, brief?}` | 400 `validation_error`, 403 `forbidden` (foreign session), 404 `not_found` |
| GET | `/api/chat/session/:id?profileId=` | query required | 200 `{session:{id,stage}, transcript[], question?, brief?, proposals?}` | 403 `forbidden`, 404 `not_found` |
| POST | `/api/auth/relink` | `{email, name}` | 200 `{profileId, name}` (exact case-insensitive email+name match) | 400 `validation_error`, 404 `not_found` (no email/fields ever returned on failure) |

`POST /api/chat/start` resumes context: an **active** brief jumps straight
to `proposals` with regenerated suggestions; a **draft** brief enters
`resume_offer` (review the draft or start fresh); otherwise a fresh
`seeking` greeting with starter chips.

`POST /api/chat/message` routes on the session stage:
- `seeking` → parses the request into a guide session; <10 chars re-prompts;
  otherwise asks the first follow-up, or finishes immediately if none.
- `followup` → records/skips the pending question (free text, single/multi
  option matching, or `skip`/`pass`); asks the next question or completes the
  guide → draft brief → `brief_review`. Invalid answers → 400.
- `brief_review` → `approve` (needs the brief's `shared_text` filled, then
  approves with consent flags and computes proposals), `edit` (asks which
  brief field, or which part), or `startover`.
- `editing` → applies the rewrite to one brief field; `cancel`/`never mind`
  restores the brief card.
- `proposals` → points at the suggestion cards; "start a new brief" asks for
  confirmation first (`confirm_replace`).

**Proposals gating (consent-first, same as `/api/briefs/:id/proposals`):**
proposals are computed only when the brief is `active` **and** holds
`consent_save`. They are never computed in the `brief_review` stage.
`private_notes` never appear in any chat payload; proposals carry no scores.

### Message shapes

- Bot text: `{role:"bot", kind:"text", text}`.
- Question: `{role:"bot", kind:"question", text, questionId, input
  ("free"|"single"|"multi"), options:[{value,label}], skippable}`.
- Brief card: `{role:"bot", kind:"brief", text, brief:{id,status,who_text,
  intention_text,good_fit_text,offer_text,logistics_text,boundaries_text,
  shared_text}}` — never `private_notes`, never `email`.
- User: `{role:"user", kind:"text", text, ts}`.
- The transcript stores both sides; `GET /api/chat/session/:id` returns it
  plus stage context (`question` for `followup`, `brief` for
  `brief_review`/`editing`, `proposals`+`brief` for `proposals`) so the
  frontend can rebuild the thread after a reload.

`POST /api/auth/relink` is for a frontend that lost its stored profile id:
on an exact (case-insensitive) email+name match it returns only
`{profileId, name}`; otherwise 404 `not_found`.

## Addendum — v13: Synchronicity Mode (2026-10-02)

A beacon is a short, time-bound signal a member chooses to be matched on:
self-input (they name their own recurring synchronicity) or a draw from the
curated deck (`src/sync-deck.js`, 48 human-reviewed starter cards; the spec
targets 100-150). One active beacon per member at a time (partial unique
index `uq_beacons_active`), 7-day expiry.

Matching is exact-normalized-text only in the MVP (lowercase, trim,
collapsed whitespace, light singularization; no resonance/cluster matching).
The match check runs synchronously at beacon creation (deterministic,
testable). On an eligible match, both beacons become `matched`, a
`beacon_matches` row is created in `proposed` status, and an introduction is
created through the existing staged mutual-consent flow (requester = the
later beacon holder). The introduction note carries the shared-beacon
reason in low-claim copy, e.g. "You both carried 'river' this week."
Proposals appear in the normal Requests view (`GET /api/introductions`).

Eligibility mirrors `POST /api/connections/request`: both members opted
into introductions, unpaused, discovery enabled, no block either way, no
decline block either way, and no live (non-withdrawn/declined/ended)
introduction between the pair.

Beacons are private: never on profiles, never searchable, never browsable.
Only the matched counterpart sees the shared word, inside the introduction
note at proposal stage. Expiry is handled lazily on every beacon read
(`expireStaleBeacons`) plus a host-only sweep; there is no cron.

### Schema v13 (`PRAGMA user_version = 13`)

| Table | Columns |
|---|---|
| `beacons` | `id`, `profile_id` FK → profiles ON DELETE CASCADE, `source` (`self_input`\|`deck_draw`), `raw_text`, `normalized_text`, `card_id` nullable, `intention_type` nullable (`conversation`\|`practice_partner`\|`collaborator`\|`local_connection`\|`open`), `status` (`active`\|`matched`\|`expired`\|`withdrawn`), `created_at`, `expires_at` |
| `beacon_matches` | `id`, `beacon_a_id`/`beacon_b_id` FK → beacons ON DELETE CASCADE, `match_type` (`exact`, `resonance` reserved for phase 2), `status` (`proposed`\|`accepted`\|`declined`\|`expired`), `proposed_at`, `introduction_id` nullable FK → introductions ON DELETE SET NULL |

Partial unique index `uq_beacons_active ON beacons(profile_id) WHERE status = 'active'`.

### Endpoints

- `GET /api/sync/deck` → `{cards:[{id,word,prompt}]}`. Curated content, safe to expose.
- `POST /api/sync/beacons` — body `{source, text?, cardId?, intentionType?}`.
  `self_input`: `text` required 1-60 chars, passes text moderation (links,
  contact info, mentions, promotions blocked with a plain message).
  `deck_draw`: `cardId` must exist. 409 `conflict_state` when an active
  beacon already exists. 201 → `{beacon, match}` where `match` is null or
  `{id, status, sharedWord, introductionId, introduction}`.
- `GET /api/sync/beacons/mine` → `{beacons:[...]}` (caller's own, active + history).
- `POST /api/sync/beacons/mine/withdraw` → withdraws the active beacon (404 when none).
- `GET /api/sync/matches/mine` → `{matches:[{id, status, sharedWord, otherProfileId, introductionId, introduction, proposedAt}]}`.
- `POST /api/sync/sweep` — host-only (`requireHost`); marks past-expiry
  beacons `expired` and closes stale proposed matches. Returns
  `{swept:{beaconsExpired, matchesExpired}}`.

Beacon wire shape: `{id, source, text, word, cardId, intentionType, status,
createdAt, expiresAt}`.

### Frontend

Modes screen gains a ninth card ("Synchronicity") with two paths: "Name
your own" (text input) and "Draw from the deck" (calm shuffle/pause/reveal,
"Here is what came up.", accept / redraw once per draw session / use my own

  `connected`, `clarity_agency`, `pressure`, `suggestion_volume`
  (choice `fewer|same|more`), `supportive_now` (text, optional),
  `offline_time`, `ai_humility`, `pause_autonomy`. Copy is non-clinical;
  frontend frames history as "Your reported pattern".
- `POST /api/flourishing/checkin` `{profileId, responses:[{questionKey,answer}]}`
  → 201 `{checkin:{id,createdAt}}`. Answers normalized server-side
  (yesno→`yes`/`no`, scale→`1`–`5`, choice→lowercase, text trimmed ≤2000).
  400 `validation_error`; profileId must match the session caller (403).
- `GET /api/flourishing/checkins/mine?profileId=` → 200
  `{checkins:[{id,questionKey,answer,createdAt}]}` newest first, caller's own only.

### Introduction feedback + real-life intentions

- `POST /api/introductions/:id/feedback`
  `{profileId, feltSafe:boolean, quality?:1-5, notes?:≤500}` → 201
  `{feedback:{id,introductionId,profileId,feltSafe,quality,notes,createdAt}}`.
  403 unless caller is a participant; 409 `already_submitted`.
- `POST /api/introductions/:id/real-life-intention` `{profileId, intention:1–300}`
  → 200 `{introduction}` (participant-only).
- `POST /api/introductions/:id/real-life-intention/complete` `{profileId}`
  → 200 `{introduction}` (participant-only). Introduction wire gains
  `realLifeIntention`, `intentionCompleted`.

### Host analytics

- `GET /api/host/analytics` (host-only, `requireHost`) → 200
  `{realWorldAction30d:{pct,n}, introductionQuality:{avgQuality,pctFeltSafe,n},
  connectionGains:{pct}, offlineTime:{pct}, safety:{incidents30d,avgResolutionHrs},
  autonomy:{pctPauseConfident}, aiHumility:{pct}, computedAt}`.
  Check-in metrics trail 30 days; `pct` = % of distinct answerers (`yes`, or
  ≥4 for `connected`); `avgResolutionHrs` = mean `updated_at − created_at`
  for reports closed in the last 30d (`null` when none). **No engagement
  metrics are tracked or exposed** (no DAU, session time, message volume,
  streaks).

### Reporting, preferences, proposals, synchronicity

- `POST /api/reports` categories extended (additive): `unwanted_contact`,
  `manipulative_spiritual_claims`, `coercion`, `exploitation`, `harassment`,
  `unsafe_event`, `harmful_ai_output` (labels in `src/constants.js`).
- `PATCH /api/profiles/:id` (and the create path) accept
  `consentSettings.recFrequency` (`daily|weekly|paused`, default `weekly`)
  and `consentSettings.quietHours` (`{start:'HH:MM',end:'HH:MM'}`; `null` clears).
- Onboarding persists extended `connectionPrefs`: `intentions[]` (0–9),
  `connectionLevels[]` (0–5), `topicsOut[]` (subset of the fixed interest list),
  `privacyLevel` (`private|community|discoverable`, default `community`),
  `locationRadius` (`local|regional|anywhere`, default `anywhere`),
  `onlineMode` (`online|offline|hybrid`, default `hybrid`),
  `commBoundaries` (≤200 chars), `syncMode` (`on|off|limited`, default `limited`).
  `createProfile`/`updateProfile` merge `connectionPrefs` rather than picking keys.
- Proposals now carry `firstStepSuggestion: 'group'|'direct'` +
  `firstStepSuggestionCopy` (from `match.js` `suggestFirstStep()`, sensitive
  contexts such as grief/trauma suggest a small group first — suggest, never
  block). The legacy `suggestedFirstStep` string is untouched.
- Match copy reframed: reasons use the resonance pattern ("SEREN noticed a
  possible point of resonance based on … This is only an optional introduction
  — not a prediction or judgment about compatibility."). No fate/destiny/proof
  language anywhere (locked by tests).
- `GET /api/sync/deck` cards now include `lens` (`symbolic|psychological|
  spiritual|practical`) and `framing`. Beacon create/mine outputs and
  `GET /api/sync/matches/mine` include `framing: "This is a creative
  reflection prompt, not a prediction, diagnosis, or verified external message."`
  The beacon-match introduction note appends the framing.

### Guide: new message kind

- Chat message kind `real_life_prompt`: `{role:'bot', kind:'real_life_prompt',
  text, skippable:true}` — "What would you like to bring into your real life
  in the next 24 hours?" Emitted after brief approval (in chat transcript)
  and on introduction accept (as top-level `realLifePrompt` on the accept
  response payload, with `introductionId`; absent on decline). Answering or
  skipping never gates progress. Guide behavior rules live in the
  `GUIDE_BEHAVIOR_RULES` block atop `src/guide.js` (agency-first phrasings,
  epistemic humility, banned phrases, crisis → professional support).
